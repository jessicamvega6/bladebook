Erasure by Token

Every identifier on a surviving record is replaced with the same stable token, S_7f3a. The name is gone and the mapping table is deleted — but the token still stitches the rows together, and the stitched-together shape is a person. This is pseudonymisation, and it does not discharge the request.

The hub is the finding. Nothing in the table stores that node — it is drawn entirely by the three rows below it agreeing on a value. Deleting the mapping did not remove it, because the mapping was never what made the rows linkable. The token is.

Why this fails as erasure

Regulators test re-identification three ways. A stable token fails all three, which is why pseudonymised data is still personal data rather than anonymous data.

Singling out Can you isolate one individual's records from the set? Yes — filter on the token
Linkability Can you connect two records as being about the same person? Yes — that is its job
Inference Can you deduce attributes about them from what remains? Yes — schedule, spend, attendance

At BladeBook's scale, the coach is the re-identification vector

A roster is around thirty students. The surviving rows describe someone who took 45-minute lessons at 4pm on Tuesdays from January to May, cancelled twice in March and stopped in the spring. A coach names that child immediately, from memory. No lookup table is required, so deleting the lookup table changes nothing.

This is why "we removed the name" is not a defence. Removing the name removes the label; the pattern does the identifying.

Pseudonymisation is not worthless — GDPR Article 32 recommends it as a security control, and it genuinely narrows what a breach exposes. It is simply a different job. Using it to answer an erasure request is the specific mistake.

What this buys, and why it is still the wrong trade

The coach keeps per-student history. "Mia paid me $2,400 last year" remains answerable, and for a coach that is a genuine loss to accept under the other option. This is the entire attraction of tokenising, and it is worth naming honestly rather than pretending the choice is obvious.

But that sentence is answerable because the data still identifies a child — the precise thing the request asked you to stop doing. The feature and the defect are the same mechanism, so you cannot keep one without the other.

The tax record needs totals, not per-person breakdown. Since totals survive either way, the reporting loss under the constant option is real but not load-bearing — which is what makes it the defensible choice.
